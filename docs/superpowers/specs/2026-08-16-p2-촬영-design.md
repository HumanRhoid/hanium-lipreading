# P2 촬영 화면 설계

작성일: 2026-08-16
상태: 설계 확정 대기
관련: [`api-spec.md`](../../api-spec.md), [`ui-설계-인수인계.md`](../../ui-설계-인수인계.md)

## 1. 목적

환자가 카메라 앞에서 15개 문구 중 하나를 발화하고, 그 영상이 백엔드
WebSocket으로 전송돼 인식 가능한 상태가 되게 한다.

이 화면의 성공 기준은 "예쁘게 보이는 것"이 아니라 **모델이 맞힐 수 있는
입력을 만들어내는 것**이다. 촬영 조건이 정확도를 직접 좌우하므로
(`ui-설계-인수인계.md` §3.3) 가이드를 안내문이 아니라 제약으로 구현한다.

## 2. 전제

- 태블릿 가로 거치, 1280×800 기준. 환자 1인이 직접 조작한다.
- 카메라 원본은 그대로 두고 **전송 직전 640×360으로 축소**해 JPEG 인코딩한다
  (`api-spec.md` §4). 프리뷰 해상도와 전송 해상도는 별개다.
- 전송률 **25fps 고정**, 프레임 간격 약 40ms를 클라이언트가 맞춘다.
- 녹화 길이 **3초 고정** → 75프레임. 하한 30·상한 250 양쪽에서 안전하다.

  15개 문구의 실제 발화는 통상 2초이며 예외가 없다. 3초로 잡는 이유는
  카운트다운이 끝난 뒤 입을 떼기까지의 지연과 발화 종료 후 여유를 포함하기
  위해서다. 정확히 2초(50프레임)로 자르면 프레임 드롭 40%에서 하한에 닿지만,
  3초는 60% 유실까지 견딘다.

## 3. 화면 상태

다섯 상태를 가지며, 한 화면 안에서 전이한다. 별도 라우트로 나누지 않는다.

```
IDLE ──(가이드 충족)──> READY ──(시작 탭)──> CONNECTING
                                                  │ ready 수신
                                                  ▼
                                              COUNTDOWN (3초)
                                                  │
                                                  ▼
                                              RECORDING (3초)
                                                  │ stop 전송
                                                  ▼
                                              P3 결과 화면
```

### IDLE — 얼굴이 가이드를 벗어남

- 프리뷰 중앙에 얼굴 실루엣 가이드. 높이는 화면 세로의 2/3.
- 가이드 테두리 회색.
- 상태 배지 1줄, 상황에 따라 하나만 노출:
  `조금 더 가까이 오세요` / `조금 더 밝은 곳에서 해주세요` / `정면을 봐주세요`
- 시작 버튼 비활성(회색, 라벨 `얼굴을 맞춰주세요`).

### READY — 가이드 충족

- 가이드 테두리 성공색 + 체크 아이콘.
- 배지 `준비됐어요`.
- 시작 버튼 활성. 라벨 `말하기 시작`.

### CONNECTING — WebSocket 수립

시작 탭 직후. 화면 중앙에 로딩 인디케이터 + `준비 중이에요`.

**이 단계에서 `ready`를 받은 뒤에 카운트다운을 시작한다.** 순서가 중요하다:

```
connect → start → ready 수신 → 카운트다운 3초 → 프레임 전송 3초 → stop
```

이렇게 하면 두 타임아웃을 모두 피한다:
- `START_TIMEOUT_SECONDS`(기본 5초): connect 직후 즉시 `start`를 보내므로 여유.
- `STREAM_IDLE_TIMEOUT_SECONDS`(기본 10초): `ready` 후 카운트다운 3초 뒤
  첫 프레임이 나가므로 여유.

카운트다운을 먼저 돌리고 나중에 연결하면 `MODEL_NOT_READY`·`SERVER_BUSY`가
카운트다운 이후에 터져서 사용자가 헛되이 준비하게 된다. 연결을 먼저 한다.

두 타임아웃 기본값은 배포 설정으로 바뀔 수 있으므로 **클라이언트가 숫자를
하드코딩하지 않는다**(`api-spec.md` §3). 위 순서는 값이 바뀌어도 안전한 쪽이다.

### COUNTDOWN — 3·2·1

- 화면 중앙에 대형 숫자(320px 이상), 1초 간격.
- 하단에 `숫자가 사라지면 말씀하세요`.
- 프리뷰는 계속 보이되 밝기를 낮춰 숫자를 부각한다.
- 화면 아무 곳이나 탭하면 취소하고 IDLE로 복귀(WebSocket close).

### RECORDING — 3초

- 가이드 테두리 녹화색, 화면 가장자리에 녹화 중임을 알리는 테두리 글로우.
- **원형 진행 링**으로 남은 시간 표시. 숫자 카운트는 쓰지 않는다
  (읽는 데 인지 부하가 걸려 발화를 방해한다).
- 3초 경과 시 자동으로 `{"type":"stop"}` 전송 → P3로 전이.
- 화면 아무 곳이나 탭하면 취소.

`프레임`이라는 단어는 어느 상태에서도 노출하지 않는다.

## 4. 가이드 판정

가이드 충족 여부는 **클라이언트에서 판정**한다. 서버는 촬영 조건을 검사하지
않는다(해상도·JPEG 유효성만 본다).

판정 기준 세 가지:

| 항목 | 기준 | 미충족 시 배지 |
|---|---|---|
| 얼굴 크기 | 얼굴 bounding box 높이가 프리뷰 세로의 2/3 이상 | `조금 더 가까이 오세요` |
| 밝기 | 얼굴 영역 평균 휘도가 임계값 이상 | `조금 더 밝은 곳에서 해주세요` |
| 정면 | yaw·pitch가 허용 범위 내 | `정면을 봐주세요` |

여러 조건이 동시에 미충족이면 위 표 순서대로 **하나만** 노출한다. 두 개를
동시에 띄우면 사용자가 무엇부터 고쳐야 할지 알 수 없다.

판정이 매 프레임 깜빡이지 않도록 **0.5초 디바운스**를 둔다. READY→IDLE 복귀는
0.5초 연속 미충족일 때만 발생한다.

구현 수단(MediaPipe Face Mesh 등)은 프론트 판단에 맡긴다. 이 문서는 기준만
정의한다.

## 5. 오류 처리

`api-spec.md` §5는 오류 코드 **12종**을 정의한다. 인수인계 문서의 8종은
불완전하다. 아래가 완전한 목록이며 UI는 이 12종을 모두 처리한다.

UI는 서버가 보낸 한글 `message`를 그대로 쓰지 않고 **자체 문구를 갖는다**.
서버 문구는 개발자 확인용이다.

### 5.1 인라인 배너 — 사용자가 즉시 고칠 수 있는 것

촬영 화면 상단에 배너로 띄우고 IDLE 상태를 유지한다. 화면을 떠나지 않으므로
바로 다시 시도할 수 있다.

| code | UI 문구 |
|---|---|
| `INSUFFICIENT_FRAMES` | 너무 짧았어요. 조금만 더 길게 말씀해 주세요 |
| `VIDEO_TOO_LONG` | 너무 길었어요. 한 문장만 말씀해 주세요 |
| `INVALID_FRAME` | 카메라를 확인해 주세요 |
| `FRAME_TOO_LARGE` | 카메라를 확인해 주세요 |
| `VIDEO_TOO_LARGE` | 카메라를 확인해 주세요 |

`FRAME_TOO_LARGE`는 close code `1009`로 먼저 끊길 수 있다. **클라이언트는
`1009`를 같은 입력 오류로 처리한다**(`api-spec.md` §4).

3초 고정·25fps 설계에서는 `INSUFFICIENT_FRAMES`와 `VIDEO_TOO_LONG`이 원칙적으로
발생하지 않는다. 프레임 드롭이 극심하거나 타이머가 어긋난 경우의 방어선이다.

### 5.2 중앙 모달 — 기다려야 하는 것

| code | UI 문구 | 버튼 |
|---|---|---|
| `MODEL_NOT_READY` | 아직 준비 중이에요. 잠시 후 다시 해주세요 | `다시 시도` |
| `SERVER_BUSY` | 지금 이용자가 많아요. 잠시 후 다시 해주세요 | `다시 시도` |
| `STREAM_IDLE_TIMEOUT` | 연결이 끊겼어요 | `다시 시작` |
| `SESSION_LIMIT_REACHED` | 연결이 끊겼어요 | `다시 시작` |
| `INTERNAL_ERROR` | 문제가 생겼어요 | `다시 시작` |

### 5.3 화면 없음 — 개발 오류

| code | 처리 |
|---|---|
| `INVALID_MESSAGE` | 클라이언트 버그. `INTERNAL_ERROR`와 같은 모달 + 콘솔 로깅 |
| `UNSUPPORTED_MODE` | 동일. v1은 `mode`를 생략하므로 발생하면 안 된다 |

### 5.4 재연결

`api-spec.md` §6의 재연결 정책 표를 그대로 따른다. UI가 알아야 할 것은
**자동 재연결 중에도 사용자에게는 `다시 시도` 버튼이 보인다**는 점이다.
백그라운드 재시도(지수 backoff)는 화면에 노출하지 않는다. 사용자에게
"재시도 3/5회" 같은 상태를 보여줄 이유가 없다.

탭이 백그라운드로 가면 자동 재연결을 멈추고, `visibilitychange`로 돌아왔을 때
IDLE 상태에서 다시 시작한다.

## 6. 접근성

- 본문 최소 32px, 카운트다운 숫자 320px 이상, 버튼 라벨 40px 이상.
- 터치 타깃 최소 88×88px. 주요 버튼은 화면 하단 1/3에 배치한다.
- 대비 7:1 이상. **색만으로 상태를 전달하지 않는다** — 가이드 충족은
  테두리 색 + 체크 아이콘 + 배지 문구 세 가지를 동시에 바꾼다.
- 취소는 화면 전체가 탭 영역이다. 작은 X 버튼을 두지 않는다.

## 7. 이 설계가 요구하는 백엔드 변경

없다. P2는 현재 `api-spec.md` v1 계약만으로 완전히 구현 가능하다.

## 8. 열린 항목

- **3초 고정값**: 실제 발화가 통상 2초이고 예외가 없다는 팀 확인에 따른
  값이다. 앞뒤 여유 1초를 포함한다. 운영 중 `INSUFFICIENT_FRAMES`가
  관측되면 늘린다.
- **밝기·정면 임계값**: 수치 미정. 프론트에서 실측 후 채운다.
- **프리뷰 해상도**: 현재 프론트는 1280×720 프리뷰다(`api-spec.md` §8).
  가이드 판정을 프리뷰 기준으로 할지 축소본 기준으로 할지 정해야 한다.
  판정은 프리뷰 기준, 전송은 640×360으로 분리하는 쪽을 권한다.
