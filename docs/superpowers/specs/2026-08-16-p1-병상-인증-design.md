# P1 병상 인증·기기 설정 설계

작성일: 2026-08-16
상태: **설계 보류 — 백엔드 정책 결정 필요**
관련: [`api-spec.md`](../../api-spec.md), [`erd-spec.md`](../../erd-spec.md), [`backend-sot.md`](../../backend-sot.md)

## 1. 먼저 짚어야 할 충돌

로그인 요구사항은 **현재 백엔드 SoT와 정면으로 충돌한다.** UI를 그리기 전에
팀이 결정해야 한다.

`erd-spec.md` §7은 "의도적으로 저장하지 않는 데이터"로 다음을 명시한다:

> 사용자·OAuth 정보
> IP, User-Agent와 브라우저 fingerprint

`api-spec.md` §7도 같은 방향이다:

> Origin 검사는 인증을 대체하지 않는다. **인증이 없는 현재 버전은 제한된
> 데모 환경에서만 운영한다.**

즉 현재 시스템은 인증을 "아직 안 만든 것"이 아니라 **의도적으로 배제한 것**이다.
`session` 테이블에도 사용자를 가리키는 컬럼이 없다.

로그인을 넣는다는 것은 다음을 전부 새로 만든다는 뜻이다:

- 인증 API (`api-spec.md`에 HTTP는 health 2개뿐이다)
- 계정·병상·기기 테이블과 `session`과의 관계
- 토큰 발급·갱신·폐기, WebSocket 인증 방식
- 개인정보 처리방침 (의료 환경 + 얼굴 영상 = 민감정보)

**이건 UI 결정이 아니라 아키텍처 결정이다.** 백엔드 담당자와 합의 없이
UI를 확정하면 버려질 화면을 그리게 된다.

## 2. 그래서 무엇을 먼저 정해야 하나

세 가지를 순서대로 정한다.

### 2.1 인증의 목적이 무엇인가

선택된 목적은 세 가지였다: 발화 기록 조회, 보호자 알림, 개인화 학습.
그런데 **각각이 요구하는 인증 강도가 다르다.**

| 목적 | 필요한 것 | 강도 |
|---|---|---|
| 기록 조회 | 병상 식별자면 충분 | 낮음 |
| 보호자 알림 | 수신자 연락처 + 동의 | 중간 |
| 개인화 학습 | 얼굴 영상 보관 + 명시적 동의 | **높음 — 민감정보** |

개인화 학습이 가장 무겁다. `erd-spec.md` §7은 원본 영상과 JPEG bytes를
저장하지 않는다고 명시하는데, 개인화 학습은 그걸 저장해야 가능하다.
**SoT를 뒤집는 변경이다.**

### 2.2 계정의 단위가 무엇인가

"병원·병상 단위"로 정했다. 이 경우 데이터 모델은 이렇게 된다:

```
HOSPITAL ─< WARD ─< BED ─< DEVICE
                     │
                     └─< SESSION (기존 테이블에 bed_id FK 추가)
```

환자 개인 계정이 아니므로 **개인정보 부담이 크게 줄어든다.** 병상은
자리이지 사람이 아니다. 이건 좋은 선택이다.

단, 개인화 학습은 "이 병상을 쓰는 사람"에 종속되므로 **환자가 바뀌면
학습 데이터를 리셋해야 한다.** 병상 단위 계정과 개인화 학습은 궁합이
나쁘다. 퇴원·전실 처리 절차가 UI에 필요해진다.

### 2.3 언제 로그인하나

관리자가 기기 설치 시 1회. 이후 세션 장기 유지. 환자는 로그인 화면을
보지 않는다. 이 부분은 충돌이 없고 그대로 진행 가능하다.

## 3. 조건부 화면 설계

위 결정이 나기 전이지만, "병상 단위 · 관리자 1회 로그인"까지는 확정이므로
그 범위의 화면은 미리 정의한다.

### 3.1 기기 등록 (최초 1회)

관리자가 태블릿을 병상에 설치할 때 한 번 거친다.

```
① 로그인        아이디 / 비밀번호, 관리자 계정
② 병상 선택      병동 → 병상 목록에서 선택
③ 확인          "302호 3번 침대에 등록합니다" → 확정
④ 환자 홈으로    이후 재부팅해도 이 화면으로 돌아오지 않음
```

- 이 화면들은 **관리자용이므로 환자용 대형 UI 규칙을 따르지 않는다.**
  일반 웹 폼 크기(본문 16px, 버튼 40px)로 충분하다.
- 텍스트 입력이 있는 유일한 화면이다. 환자 경로에는 키보드가 없다.

### 3.2 환자 홈 (기기 등록 후 기본 화면)

```
┌────────────────────────────┐
│         302호 3번          │  ← 작게, 상단
│                            │
│      말하고 싶은 게         │
│        있으신가요?          │
│                            │
│      [  시작하기  ]         │  ← 대형 버튼
└────────────────────────────┘
```

- 병상 표시는 관리자가 기기를 확인하기 위한 것. 작게 둔다.
- 로그아웃·설정 진입은 **숨긴다.** 상단 병상 표시를 3초 길게 눌러야
  설정이 열린다. 환자가 실수로 로그아웃하면 복구할 수 없다.

### 3.3 설정 (관리자 전용, 숨김 진입)

- 병상 재설정
- 카메라 선택
- 로그아웃
- 앱 버전·서버 연결 상태

진입 시 관리자 비밀번호를 다시 묻는다.

## 4. 세션 유지 방식

토큰을 로컬 저장소에 보관하고 만료 전 자동 갱신한다.

**만료되면 안 된다.** 새벽에 토큰이 만료돼 환자가 로그인 화면을 마주하면
그 순간 이 기기는 쓸모가 없어진다. 다음 중 하나가 필요하다:

- 장기 refresh token + 백그라운드 자동 갱신
- 또는 기기 인증서 방식(계정이 아니라 기기가 인증됨)

기기 단위 인증이 이 시나리오에 더 맞는다. 사람이 아니라 설치된 장비가
권한을 갖는 구조이기 때문이다.

**토큰 만료 시 UI**: 로그인 화면으로 튕기지 않는다. 환자 홈을 유지하되
`시작하기`를 비활성하고 `관리자를 불러주세요`를 표시한다.

## 5. 결론

**P1은 지금 Figma로 만들지 않는다.**

§3의 화면들은 §1·§2의 결정이 뒤집히면 함께 뒤집힌다. 특히 개인화 학습을
포함하느냐에 따라 동의 절차가 인증 흐름 안으로 들어와 구조가 달라진다.

대신 **P2·P3를 먼저 Figma로 만든다.** 이 둘은 현재 `api-spec.md` v1
계약만으로 완결되고, 인증 결정에 영향받지 않는다. 환자 홈(§3.2)만
P2 진입점으로 함께 그린다.
