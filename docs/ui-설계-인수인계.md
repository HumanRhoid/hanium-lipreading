# UI 설계 인수인계

작성일: 2026-08-15
목적: Figma UI 설계를 별도 세션에서 진행하기 위한 배경 정리

## 1. 프로젝트 개요

말하기 어려운 환자가 **입 모양만으로 의사를 전달**하도록 돕는 립리딩 보조 도구다.
한이음 드림업 4인 팀 프로젝트이며 이름은 "구순을 읽자"다.

사용자는 카메라 앞에서 정해진 문구 중 하나를 말하고, 시스템이 입 모양을 읽어
어떤 문구인지 판별해 화면에 띄운다. 소리는 쓰지 않는다.

## 2. 인식 대상 문구 (15개, 고정)

| ID | 문구 | ID | 문구 |
|---|---|---|---|
| 0 | 가래가있어요 | 8 | 아파요 |
| 1 | 간호사불러주세요 | 9 | 어지러워요 |
| 2 | 더워요 | 10 | 자세바꿔주세요 |
| 3 | 도와주세요 | 11 | 진통제주세요 |
| 4 | 물주세요 | 12 | 추워요 |
| 5 | 배고파요 | 13 | 토할거같아요 |
| 6 | 보호자불러주세요 | 14 | 화장실가고싶어요 |
| 7 | 숨쉬기힘들어요 | | |

라벨 ID는 문구를 가나다순으로 정렬해 부여한다. 문구 추가·변경 계획은 현재 없다.

## 3. UI 설계에 반드시 반영해야 할 제약

### 3.1 정확도가 낮다

화자 독립 조건에서 **정확도 약 0.58**이다. 처음 보는 사용자의 발화를 열 번 중
여섯 번 정도 맞힌다. 화자 7명 규모 데이터의 한계이며 단기간에 크게 오르기 어렵다.

**UI가 이 전제 위에서 설계돼야 한다.** 인식 결과를 단정적으로 제시하면 오답이
그대로 전달된다. 사용자가 확인하고 정정할 수 있는 흐름이 필요하다.

### 3.2 결과는 한 번만 온다

실시간 자막처럼 글자가 순차적으로 나타나지 않는다. 녹화를 끝내면(`stop`)
전체 영상을 한 번 추론해 최종 결과 하나를 보낸다. 중간 결과는 없다.

### 3.3 촬영 조건이 성능을 좌우한다

실험에서 확인된 사실이다.

- 입술이 화면에서 세로 80픽셀 미만이면 정확도가 크게 떨어진다
- 얼굴이 화면 세로의 2/3 이상을 채워야 한다
- 정면, 밝은 곳

**촬영 가이드를 UI에 녹여야 한다.** 얼굴 위치 가이드 프레임, 거리 안내,
조명 경고 같은 장치가 성능에 직접 영향을 준다.

### 3.4 최소 프레임 수 제약

30프레임 미만이면 추론하지 않고 `INSUFFICIENT_FRAMES` 오류를 낸다.
너무 짧게 녹화하면 실패한다는 뜻이고, 사용자에게 최소 녹화 시간을 알려야 한다.

250프레임을 넘어도 거부된다.

## 4. 백엔드 현황

FastAPI + WebSocket + PostgreSQL로 구현돼 있다. 명세는 `docs/api-spec.md`에 있다.

### 4.1 통신 흐름

```
WS 연결  →  ready
  ↓
start (JSON)          인식 시작
  ↓
JPEG 프레임 (binary)   반복 전송
  ↓
stop (JSON)           녹화 종료
  ↓
result → stopped → close
```

### 4.2 서버가 보내는 이벤트

```json
{"type":"ready"}
{"type":"result","text":"물 주세요","final":true,"confidence":0.91}
{"type":"error","code":"MODEL_NOT_READY","message":"인식 모델이 준비되지 않았습니다."}
{"type":"stopped"}
```

`confidence`는 선택 필드다. 있으면 0~1 범위이고, UI에서 신뢰도 표시에 쓸 수 있다.

### 4.3 오류 코드와 사용자 메시지

클라이언트에는 영문 `code`와 한글 `message`가 함께 온다. **각 오류마다 화면
상태가 정의돼야 한다.**

| code | 상황 | UI가 안내할 내용 |
|---|---|---|
| `INSUFFICIENT_FRAMES` | 녹화가 30프레임 미만 | 조금 더 길게 말해달라 |
| `INVALID_FRAME` | 해상도 불일치, 디코딩 실패 | 카메라 설정 확인 |
| `VIDEO_TOO_LONG` | 250프레임 초과 | 한 문장만 짧게 |
| `MODEL_NOT_READY` | 서버 모델 미준비 | 잠시 후 다시 시도 |
| `SERVER_BUSY` | 동시 접속 한계 | 잠시 후 다시 시도 |
| `STREAM_IDLE_TIMEOUT` | 입력 없이 대기 | 세션 만료 안내 |
| `SESSION_LIMIT_REACHED` | 최대 이용 시간 초과 | 세션 만료 안내 |
| `INTERNAL_ERROR` | 서버 오류 | 일반 오류 안내 |

### 4.4 아직 연결되지 않은 것

추론 부분이 `FakeSyncPredictor`로 되어 있다. 학습된 모델을 붙이는 작업이 남았다.
API 계약은 확정돼 있으므로 UI 설계에는 지장이 없다.

## 5. 설계해야 할 화면

최소 구성이며, 필요하면 늘려도 된다.

**① 시작 화면** — 사용법 안내, 카메라 권한 요청, 시작 버튼

**② 촬영 화면** — 카메라 프리뷰, 얼굴 위치 가이드, 녹화 시작·종료, 녹화 중 표시,
경과 시간 또는 프레임 수 피드백

**③ 결과 화면** — 인식된 문구 제시, 신뢰도 표현, 다시 시도, 확인

**④ 오류 화면 또는 상태** — 위 오류 코드별 안내

## 6. 설계 시 특히 고민할 지점

**정확도 0.58을 어떻게 다룰 것인가**가 가장 중요하다. 몇 가지 방향이 있고,
어느 쪽이든 팀 논의가 필요하다.

- 결과 하나를 크게 보여주고 "맞습니까?" 확인받기
- 신뢰도가 낮으면 다른 표현으로 안내 (예: "잘 못 들었어요, 다시 말씀해 주세요")
- 확신도를 시각적으로 구분 (색, 아이콘, 문구)

**사용 대상이 환자**라는 점도 반영돼야 한다. 손 사용이 제한적일 수 있고,
글자가 작으면 읽기 어렵다. 접근성 기준(글자 크기, 대비, 터치 영역)이 일반
서비스보다 엄격해야 한다.

**보호자·간호사가 보는 화면인지, 환자가 보는 화면인지**도 정해야 한다.
환자가 말하고 보호자가 읽는 구조라면 화면 방향이나 크기 설계가 달라진다.
